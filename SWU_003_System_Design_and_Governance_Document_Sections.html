3.5. Database Metadata

The system utilizes a relational database management system hosted on TiDB Cloud (Serverless MySQL 8.0 compatible engine) operating with utf8mb4 character set and utf8mb4_general_ci collation. The complete schema comprises twenty-seven (27) normalized tables structured across user role-based access control, donation lifecycles, relief inventory tracking, kit repacking operations, calamity distribution logistics, volunteer shift scheduling, and cryptographically verifiable digital certificates.

4.2. Governance Standards

4.2.2. Code Naming Convention

Purpose: Establishing strict code naming conventions ensures maintainability, team velocity, readability, and consistency across a full-stack polyglot environment comprising a React 18/19 SPA frontend, a PHP 8.2 backend, and a relational MySQL/TiDB database.

Specific Casing Styles and Scopes:

  • PascalCase: Exclusively applied to React UI Components (e.g., StatsSection.jsx, PartnersSection.jsx, AdminLayout.jsx), React Context Providers (AuthContext.jsx, ThemeContext.jsx), and PHP Object-Oriented Classes/Exceptions.
  • camelCase: Applied to JavaScript variables, React custom hooks (e.g., useApiList, usePagination, useAuth), component props, JavaScript helper functions (e.g., fetchDonationStats(), handleVerify()), and JSON API payload attributes.
  • snake_case: Applied to all database tables and column names (e.g., inventory_items, tracking_code, proof_file, created_at) and backend PHP variables, database query parameters, and procedural helper scripts (e.g., $db_host, get_db_connection()).
  • UPPER_SNAKE_CASE: Strictly reserved for global constants, configuration definitions, and environment variables (e.g., DB_HOST, DB_PASSWORD, JWT_SECRET, VITE_API_URL, MAX_UPLOAD_SIZE_MB).
  • kebab-case: Applied to CSS class names (e.g., .stat-card, .btn-primary, .modal-backdrop), web route URLs (e.g., /admin/inventory-management, /portals/donor/certificates), and REST API file/resource endpoints.

Prefixes and Suffixes:

  • Booleans: Must begin with affirmative verbs such as is, has, can, or should (e.g., isLoading, isVerified, hasPermission, canDistribute).
  • React Custom Hooks: Must invariably start with use (e.g., useApiList, usePagination, useAuth).
  • Event Handlers: Must use handle for definition (e.g., handleDonationSubmit) and on for passed callback props (e.g., onSubmit, onStatusChange).
  • Foreign Keys: Must always be suffixed with _id matching the singular referenced table (e.g., user_id, donor_id, role_id).

Rules for Abbreviations: Cryptic abbreviations are prohibited. Standard industry abbreviations are permitted: id, db, api, url, cv, auth, lgu. Business models must use full descriptive terms (use beneficiary rather than ben, repacking_job rather than rpk_j).

Exceptions: Environment variables and constants are written in ALL_CAPS. Embedded acronyms in camelCase maintain consistent casing (e.g., parseCsvFile, fetchApiData).

4.2.3. Coding Standards

Overall Coding Philosophy: The team adheres to DRY (Don't Repeat Yourself) via centralized utility libraries and bootstrap handlers, SOLID design principles for modular API routes, KISS (Keep It Simple, Stupid) for accessible logic, and Defensive Programming via parameterized PDO SQL queries, rigorous input sanitization, and type-casting.

Style Guides Referenced:

  • Frontend (JavaScript / React): Airbnb JavaScript Style Guide and official React.dev guidelines.
  • Backend (PHP): PSR-12 (Extended Coding Style) and PSR-4 (Autoloading Standards) defined by PHP-FIG.
  • Database (SQL): SQL Style Guide (ISO/IEC 9075) with uppercase reserved keywords and lowercase identifiers.

Formatting Rules: 2-space soft indentation for JavaScript, JSX, and CSS; 4-space indentation for PHP backend code. Maximum line width is 100 characters. Semicolons are mandatory. 1TBS (One True Brace Style) is enforced across JavaScript.

Documentation: JSDoc and PHPDoc blocks are required on all shared utilities, custom hooks, and API endpoints indicating parameters, return types, and thrown exceptions. Inline comments clarify architectural rationale ('why') rather than obvious code logic ('what').

Error Handling Conventions:

API responses conform strictly to a standardized JSON response envelope:

{
  "success": true | false,
  "data": { ... } | null,
  "message": "Descriptive operational message",
  "error": "Standardized error code or null"
}

Explicit HTTP status codes must be returned (200, 201, 400, 401, 403, 404, 422, 500). Internal database errors are logged securely server-side without leaking raw credentials or stack traces to client browsers.

Enforcement Tools: ESLint and Prettier for frontend formatting; PHP_CodeSniffer (phpcs) for backend PSR-12 validation; Git pre-commit hooks configured via Husky to block non-conforming commits.

4.2.4. Environment Variables Standards

Purpose: Adhering to Twelve-Factor App methodology (Config III), all environment-specific configs, database secrets, and API credentials are completely externalized from code, ensuring zero leakage into git and seamless portability across dev, staging, and production.

Naming & Categorization:

  • DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD, DB_SSL — Database connectivity credentials.
  • BREVO_API_KEY, GEMINI_API_KEY, MAIL_FROM_EMAIL, MAIL_FROM_NAME — External cloud services.
  • VITE_API_URL, VITE_APP_ENV, VITE_APP_VERSION — Frontend client-accessible environment flags.
  • FRONTEND_URL, SESSION_LIFETIME, APP_SECRET — CORS security and session lifetime tokens.

Storage Locations: Local development uses an uncommitted .env file. Staging and Production utilize Render Environment Variables Dashboard and Vercel Project Environment Variables. A sanitized template .env.example is committed with clear documentation.

Hardcoding Policy: Passwords, database endpoints, encryption keys, and private tokens must NEVER be hardcoded. Permitted hardcoded items are limited to non-sensitive defaults (e.g., default page limit of 10, static UI strings).

Security Practices: .env* files are permanently excluded in .gitignore. Production secrets are restricted to designated administrators and rotated on a 90-day cycle or immediately upon team member offboarding.

4.2.6. Taxonomy/Metadata Standards

Purpose: Establishing taxonomy standards ensures unified classifications, predictable API contracts, and unambiguous semantic versioning across all system layers.

  • Database Schema Metadata: Tables are pluralized snake_case nouns (e.g., assistance_requests). Primary keys are consistently id BIGINT UNSIGNED AUTO_INCREMENT. Foreign keys strictly follow singular_parent_table_id. Mandatory audit columns created_at and updated_at are present on all transaction tables.
  • API Metadata: Responses include standardized HTTP headers (Content-Type: application/json, X-API-Version: 1.0.0). Paginated responses provide pagination metadata envelopes (total_records, current_page, per_page, total_pages).
  • Code Metadata: PHPDoc and JSDoc tags (@param, @returns, @throws, @deprecated) are required on all shared functions.
  • Version Control Tagging: Semantic Versioning (SemVer 2.0.0) format (vMAJOR.MINOR.PATCH) is enforced (e.g., v1.0.0 Initial Capstone Release). Commits adhere to Conventional Commits (feat:, fix:, docs:, refactor:, chore:).
  • Feature Flags: Runtime flags (e.g., FEATURE_AI_VOLUNTEER_MATCHING=true, MAINTENANCE_MODE=false) control functionality without code rebuilds.

4.2.7. Deployment Standards

Deployment Environments: 1) Development (Local machine localhost:5173 / localhost:8000); 2) UAT (Staging on Vercel and Render) for validation by Rise Above Foundation Cebu staff and SWU faculty panelists; 3) Production (Vercel Global CDN + Render Docker + TiDB Cloud Serverless) for live humanitarian relief operations.

CI/CD Deployment Process:

  • 1. Code Commit: Developer pushes code to GitHub repository branches.
  • 2. Automated Trigger: GitHub webhooks trigger Render and Vercel build pipelines.
  • 3. Build & Test: Vercel compiles and bundles the React SPA; Render compiles the Docker container with PHP 8.2 Apache.
  • 4. Health Check Verification: Render checks /api/health.php for zero-downtime container readiness before routing live traffic.
  • 5. Database Migrations: Schema changes are applied via transaction-safe migration scripts against TiDB Cloud.

Branching Strategy: Structured GitFlow model:

  • feature/*: Feature branches branched from develop.
  • develop: Continuous integration branch automatically deployed to UAT / Staging.
  • main: Protected production branch. Direct pushes are disabled. Deploys to Production.
  • hotfix/*: Critical production patches branched from main and back-merged to develop.

Approval Requirements: Merges to main require a formal Pull Request (PR) with at least two peer reviews and green status from automated build checks, authorized by the Lead Developer.

Rollback Procedures:

  • Frontend Rollback (Vercel): Vercel Dashboard -> Deployments -> Select prior stable build -> Click "Rollback to this Deployment" (executes in under 15 seconds).
  • Backend Rollback (Render): Render Dashboard -> Service Activity -> Select prior successful Docker image -> Trigger redeploy.
  • Database Rollback (TiDB Cloud): Point-In-Time Recovery (PITR) snapshots allow restoring the database to any exact second prior to deployment.
